# loop v1 — 스킬: 에이전트가 쌓이는 그릇

상태: 검토 대기 (승인 전 코드 없음)
날짜: 2026-11-15
범위: 프로젝트 (전체 설계)
개정: 4 (**스파이크 실측 반영** — 메커니즘 검증, 가치 가설 반증. §12)

---

## 1. 무엇을, 왜

loop의 목표는 두 문장입니다.

1. 사람과 에이전트가 같은 곳에서 협업한다.
2. 에이전트가 일할수록 나아진다.

1번은 Buzz 1.0이 이미 합니다. 2번은 **두 제품 모두에서 빈 칸**입니다.

- Paperclip: 이슈 #460 "Agent Persistent Memory Store"가 8개월째 열려 있고, 본문 첫 줄이
  "Agents lose all learned context between heartbeat runs"입니다. 6월 시도(#461)는 큐 정리로 닫혔고 코드에 남은 것이 없습니다.
- Buzz: 에이전트가 스스로 쓰는 engram 기억(kind 30174)이 있지만 채점도, 소유자 승인도, 측정도 없습니다.

지난 30여 턴 동안 "학습"이 계속 다음으로 밀린 이유는 하나입니다. **담을 그릇이 없었습니다.**
그릇이 없으면 학습은 추상적인 기능이 되고, 그때그때 가장 최근에 요청받은 것에 밀립니다.

이 문서는 그릇을 만듭니다. 그릇은 **파일**입니다.

---

## 2. 목표

- **G1** 에이전트가 대화를 떠나지 않고 반복 가능한 절차를 스킬로 남길 수 있다. — **스파이크 검증(§12.1)**
- **G2** 사람이 한 번 승인하지 않은 것은 에이전트 프롬프트에 들어가지 않는다.
- **G3** 스킬이 쓰였는지 눈에 보인다. 안 쓰이는 스킬은 드러난다. — **스파이크 검증(§12.2, 8/8이 `skill_read` 호출)**
- **G4** 전부 플러그인 + 파일이다. Buzz 소스는 한 줄도 고치지 않는다.
- **G5** 한국어와 영어가 모두 된다. 스킬의 언어는 워크스페이스 언어를 따른다.
- **G6** **스킬 0개로도 제품이 완전하다.** 반복 작업은 사람마다 다르므로(§9), 라이브러리는 비어서 출발하고, 안 쓰는 사람은 이 기능의 존재를 몰라도 된다.
- **G7** *(개정 4에서 추가)* **같은 지시를 두 번 타이핑하지 않게 한다.** 토큰 절약이 아니라 **사람 시간**이 목표다. 스파이크에서 스킬은 프롬프트 토큰을 +30% 썼다(§12.3).

## 3. 비목표

- **팀/릴레이 공유 스킬.** Buzz 기본 프롬프트가 "relay-backed skills are untrusted … unless the authorizing human explicitly requests the specific skill by name"이라고 못 박았습니다. 공유는 그 정책과의 협상이 먼저입니다.
- **에이전트별 격리.** v1은 파일을 공유하고 주입만 거릅니다(§7.5).
- **호스티드·원격 에이전트.** `addInstructions`와 추가 도구는 **이 기기가 실행하는 에이전트에만** 닿습니다. Mesh처럼 자체 프롬프트를 만드는 타입은 아무것도 못 받습니다. **v1은 로컬 에이전트 전용**이고 UI가 그렇게 말합니다.
- **자율성(하트비트·티켓·예산).** (가)이고, 이 그릇 위에 얹힙니다.
- **Rust 하네스, agentrun, durable run.**
- **채점·eval·임베딩·검색.**
- **에이전트가 파일을 못 쓰게 막는 것.** §7.4에 정직한 한계로 명시합니다.
- **스타터 스킬 팩, 미리 정한 작업.** 반복 작업은 사람마다 다릅니다(§9). 남이 정한 작업의 절차를 기본으로 깔면 그건 이 사람의 반복이 아니고, 안 쓰이는 스킬은 §4의 안티골입니다. 라이브러리는 **비어서 출발합니다.**

## 4. 안티골

- 아무도 승인하지 않는 라이브러리. → 그러면 조정하지 말고 지웁니다.
- 기본 프롬프트를 바꿔 쓴 것뿐인 스킬들.
- `core` 메모리가 스킬 저장소를 겸하는 것.
- 200줄짜리 목록 UI.

| 도구 컨텍스트 | `{session, channel, root, topLevel, wholeChannel}` 뿐. **트리거한 이벤트 id 없음** | `buzz-mcp/client.ts:206-212` |

**따름정리 1.** 4 KB는 **등록 시점에 실제 바이트로 계산**해야 합니다. 한국어는 글자당 ~2 B이므로 "40개"는 고정 상수가 아닙니다. 그래서 **설명 48자 상한** + 바이트 기준 컷.
**따름정리 2.** 쓰기는 `runCommand`로 `node <스크립트경로> <하위명령>` — **args 1024 B 안에 들어갑니다.** 인라인 `-e`는 안 됩니다(스크립트가 1 KB를 넘음). stdin으로 JSON을 넘기고 `maxOutputBytes`를 선언합니다.
**따름정리 3.** `AGENTS.md`는 우리 것이 아닙니다. 인덱스는 `SKILLS/INDEX.md`에 두고, **플러그인이 `AGENTS.md`에 3줄 포인터 블록을 추가**합니다(§7.6).
**따름정리 4.** 상태 저장소는 **파일**입니다. `artifactStorage`는 릴레이 스코프이고(커뮤니티 선택 필요) 플러그인 쪽에는 **레코드 쓰기 API가 없습니다**. 로컬 승인 로그로 쓸 수 없습니다.

## 6. 접근법 (검토한 것과 왜 둘이 탈락했나)

| | 무엇 | 왜 탈락 / 선택 |
|---|---|---|
| **A. 릴레이 기반 스킬** (kind 30174처럼 암호화 이벤트) | 기기·팀 간 공유, 서명·감사 | **탈락.** 기본 프롬프트가 릴레이 스킬을 untrusted로 규정하고 "사람이 이름을 대기 전에는 읽지 말라"고 지시합니다. v1의 일은 그 정책과 싸우는 게 아닙니다. |
| **B. loop 자체 에이전트 타입**(포크) | 스킬 필드, 전용 탭, 완전한 제어 | **탈락.** 한국어 퍼스트런 포크와 **같은 포크를 두 번**. 게다가 `registerTab`이 이미 에이전트별 화면을 줍니다. |
| **C. 워크스페이스 파일 + 플러그인 하나** | `SKILLS/` 폴더, 주입, 도구 3개, 승인 페이지 | **선택.** Buzz 소스 변경 0. 모든 하네스가 파일을 읽음. 플러그인이 꺼져도 파일은 남음. |
| **D. 기존 `mem/` 재사용** | 이미 있고 승인 개념도 없음 | **탈락.** 세 가지 다 나쁩니다: `core`는 65 KB 벽에 "10 KB 아래로 유지하라"는 지시가 붙어 절차를 담을 곳이 아님; 차가운 `mem_set`은 릴레이 기반이라 기기 파일이 아님; 그리고 **diff도, 버전도, 검토 화면도 없음**. 이 기능의 값어치는 "검토 가능한 파일"에서 나옵니다. |

**C를 고른 이유 한 줄:** 아티팩트가 통합보다 오래 살아남는 유일한 모양입니다.

## 7. 설계

### 7.1 배치

```
~/.buzz/
  AGENTS.md                  ← 3줄 포인터 블록만 추가(§7.6). 나머지는 건드리지 않음
  SKILLS/
    INDEX.md                 ← 생성물. 승인된 스킬 한 줄씩 (사람이 읽는 사본)
    <slug>/
      SKILL.md               ← front matter + 절차
      references/…           ← 선택
      usage.json             ← { injected, read, lastReadAt }
      .versions/<ts>.md      ← 이전 본문
    _drafts/<slug>.md        ← 에이전트가 씀. 절대 주입되지 않음
    _rejected/<slug>.md      ← + 거절 사유
    _archived/<slug>/        ← 은퇴. 인덱스에서 빠짐
    .state/
      approvals.jsonl        ← append-only 승인 로그 (정본)
      prefs.json             ← 에이전트별 켜기/끄기 캐시 (v2)
```

**정본은 무엇인가.** 파일이 정본이고, `INDEX.md`는 사람이 읽는 **생성물**입니다.
주입은 `SKILLS/*/SKILL.md`를 직접 스캔하고 front matter와 `.state/approvals.jsonl`을 대조해 만듭니다.
`INDEX.md`를 읽어서 주입하지 않습니다 — 그러면 `INDEX.md` 한 줄로 모든 에이전트의 프롬프트에 아무 말이나 넣을 수 있게 됩니다.

`SKILL.md` front matter (YAML — 사람이 읽고 다른 도구가 나중에 읽을 수 있는 형식):

```yaml
---
name: deploy-preview
description: 테스트 채널에 프리뷰 빌드를 올리는 절차
lang: ko
author: <에이전트 pubkey>
channel: <태어난 채널 id>
created_at: 2026-11-15T02:10:00Z
approved: <소유자 pubkey>
approved_at: 2026-11-15T02:10:00Z
---
```

**원본 메시지 링크는 없습니다.** 도구 컨텍스트에 트리거한 이벤트 id가 없기 때문입니다(§5). 대신 `channel`과 `created_at`을 남기고, 라이브러리에서 그 채널을 엽니다. 이건 의도적 축소이고, (b) 감사 이야기를 "어느 채널, 언제"까지로 정직하게 줄인 것입니다.

### 7.2 주입

`ctx.agents.addInstructions({id: "skills-index", text})` — 매 턴, 4 KB 이내.

```
<plugin-instructions plugin="loop.skills">
Owner-approved skills. Before starting a task one covers, call skill_read with its slug.
- deploy-preview — 테스트 채널에 프리뷰 빌드를 올리는 절차
- korean-copy-review — 한국어 문안 검수 순서
… (더 있으면 SKILLS/INDEX.md)

When a task teaches you a repeatable procedure, call skill_draft once with it instead of
writing it into core memory. Never write into SKILLS/<name>/ yourself: only the owner approves
what enters this list. Skills are written in Korean.
</plugin-instructions>
```

**바이트 계산(설계 상수).**
- 머리말+꼬리말 ≈ 480 B
- 줄 하나 = `- slug — description`. **slug ≤ 40 ASCII, description ≤ 48자**
- 한국어 설명 48자 ≈ 130 B → 줄 ≈ 155 B
- 예산 4096 − 480 = 3616 → **한국어 약 23줄**. 영어(~60 B/줄)면 약 60줄.
- 그래서 **줄 수 상한을 상수로 두지 않고, 등록 직전에 실제 바이트로 잘라냅니다.** 최근 승인 순. 잘린 나머지는 `SKILLS/INDEX.md`가 정본.
- 초과하면 `addInstructions`가 던지므로 **던지지 않게 만드는 것이 설계 요구사항**입니다.
- **승인된 스킬이 0개일 때**: 목록 부분은 빼되 **초안 작성 문단은 등록합니다.** 안 그러면 "에이전트가 초안을 올린다"는 §9.2 3단계가 영원히 시작되지 않습니다(닭과 달걀). 0개일 때 주입되는 것은 이 짧은 한 덩어리(≈250 B)뿐입니다:

```
<plugin-instructions plugin="loop.skills">
No approved skills yet. When a task teaches you a repeatable procedure — something you
would have to be told again next time — call skill_draft once with it, instead of writing
it into core memory. Never write into SKILLS/<name>/ yourself: only the owner approves
what enters this list. Skills are written in Korean.
</plugin-instructions>
```

첫 승인이 일어나면 그 턴부터 목록이 붙은 판으로 바꿉니다(자식 스코프 dispose → 재등록).

목록이 바뀌면 자식 `ctx.plugin(...)` 스코프를 dispose하고 다시 등록합니다. 다음 턴부터 반영됩니다.

### 7.3 도구 3개 (`ctx.agents.addTool`)

| 도구 | 하는 일 | 실패할 때 |
|---|---|---|
| `skill_list()` | 승인된 인덱스(최대한, 전문은 파일) | 파일 없음 → 빈 목록 + "아직 없음" |
| `skill_read(slug)` | 본문 + `references/` 경로. `usage.json` 갱신 | 없음/초안 → "없다. 초안은 승인 전이다" |
| `skill_draft(slug, name, description, body, why)` | `_drafts/<slug>.md` 작성 | 대기 중 초안 있음 → "이미 대기 중"; 거절된 슬러그 → **거절 사유를 돌려줌**; 쓰기 불가 → "대화에 남겨라" |

`why`(한 줄)는 필수입니다. 사람이 10초 만에 초안을 판단하게 하는 유일한 장치입니다.
`body` 상한은 stdin 64 KiB에서 옵니다 → **초안 본문 60 KB 상한**, 넘으면 거절하고 이유를 말합니다.

### 7.4 승인 게이트

**UI**: Settings → **Skills** (`ctx.settingsCards.register` — Steady 표면).

행: 칩(`draft` / `approved` / `rejected` / `archived` / **`approved outside loop`**), 이름, 한 줄 설명, 쓴 에이전트, 나이, 읽힌 횟수.
초안을 펼치면: **전문**, `why`, 채널 링크, 같은 슬러그의 기존 스킬이 있으면 **diff**, 그리고 `Approve` / `Edit` / `Reject`.

- **Approve** → `SKILLS/<slug>/SKILL.md`로 옮기고 front matter를 찍고, `.state/approvals.jsonl`에 한 줄 추가하고, `INDEX.md`를 다시 쓰고, 초안이 태어난 채널에 **멘션이 아닌** 짧은 글("skill X approved")을 남깁니다. 멘션이 아니므로 에이전트를 깨우지 않습니다.
- **Reject** → `_rejected/`로 옮기고 사유 저장. 같은 슬러그로 다시 `skill_draft`하면 사유를 돌려받습니다. **거절도 학습 신호입니다.**
- **Adopt** (← 빌더 검토에서 추가) → 손으로 쓴 파일, 백업에서 온 파일, 다른 기기에서 복사한 파일을 승인합니다. 이것이 없으면 밖에서 들어온 스킬이 영원히 "approved outside loop"가 됩니다. 첫 실행 때 비어 있지 않은 `SKILLS/`를 만나면 **전부 draft로 취급**하고 Adopt를 안내합니다.
- **Archive** → `_archived/<slug>/`로 이동, 인덱스에서 제거, `approvals.jsonl`에 `archived` 기록. v1의 유일한 은퇴 경로입니다. (v1에 `disabled` 칩은 없습니다 — 그건 v2의 에이전트별 토글입니다.)
- **위조 감지**: front matter가 승인을 주장하는데 `.state/approvals.jsonl`에 항목이 없으면 `approved outside loop` 칩. 20줄짜리 장치이고, 이 기능의 유일한 실질 위험을 정면으로 다룹니다.
- **초안 도착 알림**: 스킬 초안이 생기면 **조용한 알림 한 번**만 냅니다 — `ctx.notifications.register({id, label})` + `submit({sourceKey, target, title, body})`, `target`은 라이브러리의 그 행. 배너·모달·채널 공지는 없습니다. 초안은 대기열이지 업무가 아니고, 대기열이 사람을 재촉하면 아무도 이 기능을 켜두지 않습니다.
- **초안이 0개일 때**: 라이브러리는 빈 표가 아니라 §9.2의 한 문장을 보여줍니다. 에이전트가 한 번도 초안을 안 올렸는데 "스킬을 만드세요"라고 하면, 그건 사용자에게 우리가 대신 해야 할 일을 시키는 것입니다.

**정직한 한계 — 문서에 반드시 남깁니다.**
Pi 에이전트는 워크스페이스에 샌드박스 없는 `write`와 `bash`를 가집니다. 그러므로 게이트는
**사고를 막고 감사 흔적을 남기는 장치이지, 적대자를 막는 경계가 아닙니다.**
파일을 위조할 수 있는 에이전트를 파일 권한으로 막을 방법은 없습니다. 게이트가 실제로 사는 것은 셋입니다:
(a) 사람이 승인하지 않은 것은 프롬프트에 안 들어간다, (b) 각 스킬이 언제 어느 채널에서 왜 생겼는지 남는다,
(c) 나쁜 스킬이 증폭되기 전에 걸린다.

이 한계는 설치 문서에도 같은 문장으로 적혀 있습니다 — `plugins/loop-skills/README.md`의 "The gate is not a security boundary". 코드를 읽지 않는 사람이 읽는 곳은 README이므로, 한쪽에만 적으면 그쪽은 아무도 안 읽습니다.

### 7.5 에이전트별 켜기/끄기 (v2, 설계만)

파일은 공유하되 보이기는 에이전트별로. `(에이전트 pubkey, slug)` 선호를 `.state/prefs.json`에 두고,
`when`이 **동기**로 읽도록 **메모리 캐시**를 씁니다(§5 제약). 파일이 바뀌면 다시 읽고 재등록합니다.

**v1은 "승인된 전부, 모든 로컬 에이전트"로 출시**하고 TODO를 남깁니다. 에이전트가 하나뿐인 지금 토글은 쓰이지 않고, 쓰이지 않는 UI는 잘못 자랍니다.

### 7.6 망가져도 반쯤은 되는 모드

| 상황 | 결과 |
|---|---|
| 플러그인 꺼짐 | 설치 시 `AGENTS.md`에 넣은 3줄 포인터 블록(`<!-- loop:skills:start --> … <!-- loop:skills:end -->`)이 남아 `SKILLS/INDEX.md`를 가리킴. 에이전트가 `read`로 읽음. 도구는 없음 |
| `node` 없음 / 명령 거부 | 읽기 전용: 인덱스 + `skill_read` 동작, `skill_draft`는 "대화에 남겨라"고 명확히 거절 |
| `registerTab` 깨짐 | 설정 카드의 라이브러리가 정본이므로 승인은 계속 됨 |
| 인덱스 초과 | 주입은 최근 것만, 전문은 `INDEX.md` |
| 대화가 자기 폴더에 바인딩됨 | 기본 프롬프트가 절대경로로 바뀌므로 주입 블록이 `SKILLS/`의 **절대경로**를 함께 말함 |

### 7.7 언어

- 워크스페이스 언어를 플러그인 설정에 둡니다(기본값: UI 언어). 저장 위치는 `.state/prefs.json`.
- 주입 블록이 그 언어로 쓰라고 말합니다("Skills are written in Korean").
- 초안 행에 스크립트로 추정한 언어 라벨을 붙입니다(한글 음절 범위 검사 한 줄). 틀려도 무해하고, 사람이 승인 전에 눈으로 봅니다.
- 에이전트 답변 언어는 여전히 **묻는 사람을 따릅니다.** 스킬 언어만 워크스페이스에 고정됩니다. 둘은 다른 문제입니다.

### 7.8 측정 (정직하게)

스킬마다 기록: 주입된 횟수, **`skill_read` 호출** 횟수, 마지막 호출, 승인/거절.

**한계를 UI에 씁니다.** Pi는 같은 폴더에 `read`/`bash`를 가지므로 파일을 직접 읽으면 안 잡힙니다. 즉 "읽힘 0"은 "안 쓰임"의 하한이지 증명이 아닙니다. 그래서 라이브러리의 문구는 **"도구로 읽힘"**이고, "한 번도 안 읽힘"은 **정리 후보**일 뿐 삭제 근거가 아닙니다.

정작 중요한 숫자는 하나입니다. **반복 작업에서 스킬이 있을 때 턴 수와 토큰이 줄어드는가.** §9가 그 숫자를 기록합니다.

## 8. 빌더에게 남기는 것

- `ctx.notifications.register({id, label})`가 돌려주는 `submit`의 `target`으로 우리 설정 카드의 특정 행을 여는 방법(초안 알림 → 라이브러리 그 행).
- `agents.types()[i].usage(agent, {since, signal})`로 §9.1의 입력 토큰을 읽는 경로. 이건 하네스 타입이 제공하는 것이고 플러그인은 `types()`로 접근합니다. Pi·Claude·Codex 모두 이미 구현하고 있으므로 **우리가 계측기를 만들 필요가 없습니다.**
- `node` 헬퍼의 CLI 모양(`list|read|draft|approve|adopt|reject|archive|index`)과 JSON 형태. 헬퍼는 플러그인 폴더에 함께 배포하고, 플러그인이 런타임에 자기 폴더를 풀어 `args`로 경로를 넘깁니다.
- 쓰기 경로의 최종 선택: `runCommand`(args 1024 B, stdin 64 KiB, 5초, `maxOutputBytes` 선언) vs `spawn`(데스크톱 전용, 길이 제한 없음). **권장: `runCommand` 먼저**, 5초/64 KiB로 부족해지면 `spawn`.
- front matter 파서: YAML 그대로 vs 좁은 자체 파서. **권장: YAML.**
- 목록 가상화 임계값, 빈/로딩/에러 상태, 디자인 시스템 컴포넌트 선택.
- `registerTab`(에이전트별 "이 에이전트의 스킬")을 v1에 넣을지. **내 판단: 100줄 이하면 넣는다.** 사용자가 찾는 자리가 거기다. 단 라이브러리가 정본이고 탭은 편의라는 것을 주석에 남긴다.

## 9. 승인 시나리오 (작업은 사람마다 고른다)

**전제: 반복 작업은 사람마다 다릅니다.** 이 문서가 특정 작업을 정하면 그건 이 기능의 검증이 아니라 한 사람의 취향 검증입니다. 그래서 설계는 **작업을 고르지 않고, 작업을 고르는 절차를 고정**합니다.

그래서 v1은 **빈 라이브러리로 출발**합니다. 스타터 팩 없음, 예시 스킬 없음. 대신 "첫 스킬을 찾는" 경로를 제품 안에 넣습니다(§9.2).

### 9.1 공통 측정 (작업과 무관하게 같은 숫자)

어떤 작업을 고르든 아래 다섯 개만 기록합니다. 작업 이름은 사람이 붙입니다.

| 숫자 | 어디서 얻나 | 왜 |
|---|---|---|
| **턴 수** | 손으로 셉니다 (대화의 사용자 메시지 수) | n=2짜리 실험입니다. 자동화할 값이 아니고, 자동화하면 계기판만 늘어납니다 |
| **입력 토큰** | `agents.types()[i].usage(agent, {since, signal})` → `SessionUsage[].observations[].tokens.input` **+ `cacheRead` + `cacheWrite`** | 스킬 주입이 토큰을 늘리는데 이득이 없으면 손해. **`input`만 더하면 결과가 뒤집힙니다**(§12.3) |
| **벽시계 시간** | 첫 메시지 → 마지막 답변 (손으로) | 사람이 기다리는 시간 |
| **사람의 재작업 횟수** | "아니 그게 아니라"라고 다시 말한 횟수 (손으로) | 품질의 가장 정직한 신호 |
| **`core` 크기** | `~/.buzz` 기준 `mem_get core` 결과의 바이트 | 그릇 두 개가 경쟁하지 않는지 |

앞의 넷은 스킬 있음/없음 두 조건에서 비교합니다. 다섯째는 **절대 늘지 않아야** 합니다.

토큰만 코드로 읽고 나머지 넷은 사람이 적습니다. 이건 게으름이 아니라 **의도**입니다: 이 기능의 값어치는 숫자 대시보드가 아니라 "덜 설명해도 됐다"는 사람의 판단에서 나오고, 그 판단을 자동 지표로 바꾸면 §9.4의 실패 조건을 스스로 못 보게 됩니다.

### 9.2 절차 (사람이 자기 작업을 고른다)

1. **찾기** — 라이브러리가 비어 있을 때 화면은 폼이 아니라 한 문장입니다:
   *"지난주에 같은 일을 두 번 이상 시킨 게 있나요? 있으면 그걸로 시작하세요. 없으면 그냥 쓰세요. 에이전트가 알아서 초안을 올립니다."*
   - 여기에 **후보 목록을 자동으로 만들지 않습니다.** 대화를 훑어 "반복 작업 후보"를 뽑는 건 그럴듯해 보이지만 오탐이 많고, 오탐 목록은 사람을 일하게 만듭니다. 대신 아래 3번이 자연스럽게 후보를 만듭니다.
2. **기준선** — 고른 작업을 **스킬 없이 두 번** 시킵니다. §9.1의 네 숫자를 기록. (두 번인 이유: 한 번은 그날의 우연입니다.)
3. **초안이 먼저 온다** — 세 번째에 같은 일을 시키면, 주입 블록이 이미 이렇게 말하고 있습니다: *"When a task teaches you a repeatable procedure, call skill_draft once."* 즉 **사람이 스킬을 쓰는 게 아니라 에이전트가 초안을 올립니다.** 사람은 승인만 합니다.
   - 이게 §9.2 1번의 "손으로 쓰기"를 **없앤 것**입니다. 손으로 쓰는 경로는 `Adopt`로 남아 있지만(백업·이식·수동 작성), 첫 스킬의 기본 경로가 아닙니다.
4. **승인 후 두 번 더** — 같은 작업을 두 번. 같은 숫자.
5. **통과 조건** — 턴 수 또는 사람의 재작업 횟수가 줄고, **프롬프트 토큰(`input`+`cacheRead`+`cacheWrite`)이 늘지 않고**, `core`가 안 자랐다. 사람이 "결과가 같거나 낫다"고 말한다.

**주의 — 스파이크가 이 조건을 이미 반증했습니다.** 짧은 절차(규칙 6개)에서는 스킬이 **프롬프트 토큰 +30%, 턴 +1**이었습니다(§12.3). 그러므로 통과 조건을 "토큰이 준다"로 두면 안 되고, **"절차가 길어서 사람이 매번 다시 타이핑하는 비용이 `skill_read` 왕복보다 클 때만 이득"** 으로 좁혀야 합니다.

**4번이 핵심입니다.** 1~2는 기준선, 3은 **학습이 도는지**, 4~5는 **도는 학습이 이득인지**입니다. 3번은 스파이크에서 **이미 통과**했습니다(§12.1). 5번은 **이미 실패**했습니다(§12.3).

### 9.3 사람마다 다르다는 것을 제품이 어떻게 다루나

| 사람 | 첫 스킬이 될 것 | 설계가 이미 맞나 |
|---|---|---|
| 개발자 | 배포 전 체크, PR 정리, 로그 뒤지기 | ✅ 셋 다 파일·셸 작업 |
| 번역·문안 | 한국어 검수 순서, 용어집 적용 | ✅ `references/`에 용어집 |
| 기획 | 회의록 → 티켓, 주간 정리 | ✅ 절차 + 템플릿 |
| **아무것도 안 떠오르는 사람** | 없음 | 이게 정상 경로입니다. 스킬 0개로 계속 써도 제품은 완전합니다 |

마지막 줄이 이 절의 결론입니다. **스킬은 있어도 되고 없어도 되는 것이어야 합니다.** 없으면 §7.2 주입은 초안 작성 문단 하나만 남고, 도구 셋은 "아직 없음"을 돌려주고, 라이브러리는 9.2의 한 문장을 보여줍니다. 라이브러리를 안 여는 사람은 이 기능의 존재를 몰라도 됩니다.

### 9.4 이 기능이 실패했다고 말할 수 있는 조건

숫자가 안 나오는 것과 기능이 틀린 것은 다릅니다. 아래면 **기능을 접습니다**:

- 한 달 동안 초안이 0개 (아무도 반복 작업을 안 하거나, 주입 문구가 안 읽힘)
- 초안은 오는데 승인률이 20% 미만 (초안 품질이 낮음 → `why`와 예시를 고칠 문제)
- 승인된 스킬의 `skill_read`가 3주간 0 (인덱스가 안 읽힘 → 주입 위치가 틀림)
- **스킬 있음 조건에서 프롬프트 토큰이 줄지 않음** — **스파이크에서 이미 관측됨**(§12.3). §12.4에 따라 지표를 "사람이 다시 타이핑하지 않아도 됨"으로 바꾸고 재판정합니다.

## 10. 위험

| 위험 | 완화 |
|---|---|
| **스킬이 토큰을 절약한다는 착각** (스파이크에서 +30%로 반증됨, §12.3) | 목표를 G7("두 번 타이핑하지 않기")로 좁혔습니다. 짧은 절차에는 스킬을 권하지 않고, `why`가 "다음에 또 설명해야 하는 것"을 말하게 합니다 |
| **스타터 팩을 넣고 싶은 유혹** (빈 화면이 불안해서) | 넣지 않습니다. 남이 정한 작업의 절차는 그 사람의 반복이 아니고, 안 쓰이는 스킬은 §4의 안티골입니다. 빈 상태 안내가 스타터 팩보다 낫습니다(§9.2) |
| 4 KB 천장 → 목록이 잘림 → 스킬이 조용히 안 보임 | 실제 바이트로 컷, `INDEX.md`가 정본, 라이브러리가 전체 목록 |
| 워크스페이스 공유 → 한 에이전트의 스킬이 다른 에이전트에 노이즈 | 인덱스 줄에 쓴 에이전트 표시, v2 토글 |
| Windows에 `node`가 없음 | 읽기 전용 강등 + 명확한 거절 문구. `runCommand`는 플랫폼 제한이 없음 |
| 기본 프롬프트가 계속 `core`로 학습을 보냄 → 그릇 두 개가 경쟁 | 주입 블록이 어느 쪽이 이기는지 명시. §9 5번이 `core` 크기를 검사 |
| 업스트림이 자체 스킬 UI를 냄 | 아티팩트가 파일이므로 업스트림 UI가 우리 파일을 읽을 수 있음. 버려지지 않음 |
| codex 에이전트는 `~/.buzz`를 cwd로 쓰지만 스킬 폴더는 `~/.codex/skills` | v1에서 codex는 2등 시민. README에 명시 |
| `addInstructions`가 던져서 **모든 턴이 죽음** | 등록 전 바이트 검증 + 실패 시 주입 없이 계속(도구는 동작) |

### 12.3 값어치 — **반증됨**

완료된 런만, n=3씩. 프롬프트 토큰 = `input + cacheRead + cacheWrite`.

| 조건 | 프롬프트 토큰 | 어시스턴트 턴 | 정답 |
|---|---|---|---|
| **스킬 승인됨 + 최소 프롬프트** | **38,192** | **6.0** | 3/3 |
| 규칙을 다시 타이핑 | 29,367 | 5.0 | 3/3 |

**스킬이 프롬프트 토큰 +30%, 턴 +1.** 절약이 아니라 지출입니다.

원인은 산수입니다. 주입되는 인덱스 한 줄 + 스킬 본문(≈1.2 KB)이 대체하는 규칙 6개보다 **크고**, 모델이 그것을 가져오려고 `skill_read` 왕복을 한 번 더 씁니다. 스킬이 이기는 경우는 **절차가 `skill_read` 왕복보다 길 때**뿐입니다. 이 작업은 그 반대였습니다.

**측정 실수 하나를 먼저 했습니다.** pi의 `usage.input`은 **캐시 읽기를 제외**합니다. `input`만 더하면 캐시를 많이 맞힌 쪽이 싸게 보여 **결론이 뒤집힙니다**(첫 계산에서 스킬이 3.6배 비싸게 나왔고, 캐시 포함하면 1.3배). §9.1의 지표를 `input + cacheRead + cacheWrite`로 고쳤습니다.

### 12.4 이 실패를 어떻게 처리하나

**기능을 접지 않습니다. 주장을 좁힙니다.**

스킬의 값어치를 "토큰 절약"으로 팔면 안 됩니다. 데이터가 지지하는 것은 둘입니다.

1. **규칙을 사람이 다시 타이핑하지 않아도 됩니다.** 이건 토큰이 아니라 사람 시간입니다. §9.1이 이미 "턴 수, 재작업 횟수"를 손으로 적게 한 이유가 이것이고, 스파이크는 그 판단을 뒷받침합니다.
2. **규칙이 없으면 탐색이 폭주합니다.** E6r1은 규칙은 받았지만 "이전 리포트가 어디 있는지"가 없어서 **`find /`로 파일시스템 전체를 뒤졌고** 8분 워치독에 잘렸습니다. D는 아예 산출물을 안 만들고 질문으로 끝냈습니다. 즉 문맥이 빠졌을 때의 비용은 토큰이 아니라 **무한 탐색과 정지**입니다.

그래서 v1의 성공 기준은 이렇게 바뀝니다: **"같은 지시를 두 번 타이핑하지 않게 되었는가"** 그리고 **"규칙이 없어서 에이전트가 헤매는 일이 사라졌는가"**. 토큰 절약은 목표가 아닙니다.
